## ۲. آنچه در این دور انجام شد (خلاصهٔ اجرایی)

ممیزی این دور، «ممیزی خواندنی» نبود. **سرور روی MariaDB 11.8 بالا آمد و با درخواست‌های
واقعی آزموده شد.** نتیجه: سه نقص که فقط با اجرا دیده می‌شدند و هر سه تیم فرانت را در
**روز اول** متوقف می‌کردند.

### ۲٫۱ — تایپ تاریخ‌ها اشتباه بود (رفع شد)

| قبل | بعد |
| --- | --- |
| `created_at: number` در `api-types.d.ts` | `created_at: string` |
| رانتایم `2026-11-14T10:53:28.017969+03:30` می‌داد | سازگار با تایپ |
| نتیجه در UI: `new Date(number)` ⇒ **۱۹۷۰** | `new Date(string)` ⇒ تاریخ درست |
| ۲۷ فیلد معیوب | ۰ فیلد معیوب |

### ۲٫۲ — دانلود گزارش اکسل ناشدنی بود (رفع شد)

`GET /api/v1/admin/reports/excel` تایپ `string` داشت ولی `fetch().blob()` برمی‌گرداند.
اکنون `Blob` است و دو helper تازه دارد:

```ts
const { blob, fileName } = await client.download("v1_admin_reports_excel_export", {
  query: { reason: "گزارش ماهانه هیئت‌مدیره" },
});
client.saveBlob(blob, fileName);   // لینک موقت + آزادسازی حافظه + no-op امن در SSR
```

### ۲٫۳ — اولین درخواست نوشتنی پس از ورود همیشه ۴۰۳ می‌گرفت (رفع شد)

`establish_dual_session` نشست را `cycle_key` می‌کند و توکن CSRF کش‌شدهٔ فرانت باطل می‌شد.

**بازتولید واقعی:**
```
csrf before login: cRlX3vCojS5g        ← کش کلاینت پس از بوت
login: 200 | csrf rotated: True        ← چرخش نشست سمت سرور
PATCH /me with STALE csrf:  403  «CSRF Failed: CSRF token from the 'X-C…»
PATCH /me with FRESH csrf:  200  ✅
```

**اصلاح سه‌لایه:**

1. **کد اختصاصی `csrf_failed`** در کاتالوگ ۳۸ کدی — دیگر با `permission_denied` قاطی نمی‌شود.
2. **بازیابی بی‌صدا در کلاینت:** `isCsrfExpired` + `resetCsrf()` + پرچم `csrfRetried`
   ⇒ یک‌بار توکن تازه و **تکرار همان درخواست**؛ بدون حلقهٔ بی‌پایان، بدون نمایش خطا به کاربر.
3. **بستن ریشه:** `cache: "no-store"` روی بوت‌استرپ و پاک‌سازی کش CSRF پس از هر چرخش توکن.

**اثبات پس از اصلاح (اجرای واقعی):**
```
stale CSRF: 403 | code: csrf_failed | persian: True
detail: توکن امنیتی نشست منقضی شده است؛ درخواست با توکن تازه تکرار می‌شود.
fresh CSRF retry: 200
```
