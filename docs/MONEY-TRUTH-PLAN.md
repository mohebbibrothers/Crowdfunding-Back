## ۱. مسئله، بدون تعارف

امروز وقتی می‌گوییم یک پرداخت «تأییدشده» است، منظومهٔ استدلال این است:

```
کاربر گفت موفق  →  ما از درگاه پرسیدیم  →  درگاه گفت موفق  →  پس موفق است
                   ↑
                   این سؤال از *همان تراکنشی* است که داریم درباره‌اش قضاوت می‌کنیم
```

این «تأیید» است، ولی **تأیید خودگواه**. سه حالت واقعی را نمی‌گیرد:

| حالت | چه اتفاقی می‌افتد | آیا امروز می‌فهمیم؟ |
| --- | --- | --- |
| درگاه پول را گرفت ولی برای ما `verified=false` گفت (باگ درگاه) | ما پرداخت را `FAILED` می‌کنیم، ظرفیت را آزاد می‌کنیم | ❌ تا شکایت حامی |
| ما پرداخت را `VERIFIED` ثبت کردیم ولی درگاه پول را برنگرداند (تسویه نکرد) | دفتر کل ما بدهی به خیریه ایجاد کرده که پشتوانه ندارد | ❌ تا کمبود نقدینگی |
| تراکنش در فایل تسویهٔ درگاه هست ولی در سامانه اصلاً نیست | پول در حساب ما هست، مالکش را نمی‌دانیم | ❌ هرگز |

**هیچ‌کدام از این سه با `verify()` قابل کشف نیست**، چون `verify()` فقط همان تراکنش را
دوباره از همان درگاه می‌پرسد. راه کشف، **منبع داده‌ای مستقل** است: صورت‌حساب/فایل تسویهٔ بانک.

## ۲. کاری که می‌سازیم

یک لایهٔ چهارگانه که «حقیقت وجه» را از خودگواه به **مستقل و قابل‌ممیزی** ارتقا می‌دهد:

```
┌──────────────────────────────────────────────────────────────────┐
│  ۱. INGEST      ورود فایل تسویه (CSV/XLSX) — امضاشده، idempotent  │
│  ۲. MATCH       تطبیق سه‌طرفه: فایل ↔ پرداخت داخلی ↔ دفتر کل      │
│  ۳. CLASSIFY    تشخیص خودکار سناریو و اقدام تجویزی                 │
│  ۴. REMEDIATE   خوددرمانی مجاز + صف بررسی انسانی                  │
└──────────────────────────────────────────────────────────────────┘
```

قاعدهٔ طلایی: **لایهٔ تطبیق هرگز خودش پول جابه‌جا نمی‌کند.** فقط تشخیص می‌دهد و
اقدام پیشنهاد می‌کند. اقدام فقط از دو مسیر مجاز است: (الف) خوددرمانی امن و از پیش
تأییدشده برای حالت‌های بی‌ابهام، (ب) صف بررسی انسانی برای هر چیز دیگر.

## ۳. مدل داده

### ۳٫۱ `SettlementStatement` — سند فایل تسویه

```
id                  UUIDv7
gateway_name        zarinpal | sandbox
source_kind         csv | xlsx | api
statement_sha256    اثر انگشت محتوا (یکتا با درگاه) ⇒ ورود دوباره = همان سند، نه سند دوم
period_start/end    بازهٔ پوشش
row_count           تعداد ردیف فایل
declared_total_rial جمع ریالی که خودِ فایل ادعا می‌کند
computed_total_rial جمع ریالی که از ردیف‌ها محاسبه شده
integrity_ok        آیا این دو برابرند؟ (دستکاری/نقص فایل)
ingested_by         کاربر/سیستم
status              INGESTED → MATCHED → CLOSED
```

**چرا `statement_sha256` یکتا با درگاه؟** تفاوت بنیادی با آپلود فایل در اپ‌های معمولی.
اگر مدیر دوبار همان فایل را آپلود کند، نباید دو دستهٔ مغایرت با نتایج متناقض بسازیم.
همچنین اگر فایل در جای دیگری از سامانه امضا شده باشد، همبستگی فوری است.

### ۳٫۲ `SettlementRow` — یک ردیف خام

```
statement           FK
row_number          شمارهٔ ردیف در فایل (برای ارجاع دقیق به سطر خطادار)
authority           شناسهٔ تراکنش در درگاه
ref_id              شمارهٔ پیگیری
amount_rial         مبلغ به ریال
occurred_at         زمان تراکنش طبق فایل
card_pan_masked     پوشانده (اگر فایل دارد)
description         توضیح فایل
raw_payload         JSON کامل ردیف — برای ممیزی و بازبینی آینده
match_status        PENDING | MATCHED | AMOUNT_MISMATCH | MISSING_INTERNAL | MISSING_GATEWAY | DUPLICATE_IN_FILE
match_note          توضیح فارسی
payment             FK اختیاری به Payment (پس از تطبیق)
remediation         NONE | AUTO_HEALED | QUEUED_REVIEW | MANUAL_RESOLVED
```

**چرا `raw_payload`؟** فایل تسویه فردا ستون تازه اضافه می‌کند. اگر فقط ستون‌های
شناخته‌شده را ذخیره کنیم، برای بازسازی گذشته باید فایل اصلی را پیدا کنیم. ذخیرهٔ
ردیف خام یعنی **همیشه می‌توانیم گذشته را با منطق امروز بازپردازش کنیم.**

### ۳٫۳ `StatementReconciliation` — نتیجهٔ هر اجرای تطبیق

```
statement           OneToOne
matched_count / amount_mismatch_count / missing_internal_count / missing_gateway_count
auto_healed_count / queued_review_count
financial_impact_rial   خالص اثر ریالی کشف‌شده (مثبت = پول پیدا شد، منفی = پول گم شد)
is_clean            آیا هیچ مغایرتی نماند؟
```

### ۳٫۴ گسترش `Payment` — ستون حقیقت مستقل

```
truth_state         UNVERIFIED | SELF_REPORTED | STATEMENT_CONFIRMED | STATEMENT_MISSING | CONFLICT
truth_confirmed_at  زمان تأیید مستقل
truth_statement     FK اختیاری به سندی که تأییدش کرد
```

**این قلب ماجراست.** `status` همان چیزی است که «ما گفتیم». `truth_state` همان چیزی
است که **صورت‌حساب بانک** گفت. این دو هیچ‌وقت با هم قاطی نمی‌شوند.

## ۴. تطبیق سه‌طرفه — الگوریتم

### مرحلهٔ ۱: ورود (`ingest_settlement_statement`)

1. محاسبهٔ `sha256` محتوا → اگر سندی با همین درگاه+هش هست، برگردان آن (idempotent).
2. پارس ردیف‌ها با نرمال‌سازی:
   - مبلغ: «۱٬۲۵۰٬۰۰۰» / «1250000» / «1250000.00» → `int` ریال. **هیچ‌گاه `float`.**
   - تاریخ: شمسی و میلادی، ISO و `YYYY/MM/DD` → `datetime` aware.
   - `authority` trim + uppercase.
3. کنترل صحت: `computed_total == declared_total`؟ اگر نه ⇒ `integrity_ok=False` و
   **کل سند مشکوک** است: تطبیق اجرا می‌شود ولی نتیجهٔ آن هرگز خوددرمانی نمی‌کند.

### مرحلهٔ ۲: تطبیق (`reconcile_settlement_statement`)

برای هر ردیف:

```
if authority در فایل تکراری باشد          → DUPLICATE_IN_FILE  (فایل معیوب است)
elif Payment با این authority وجود ندارد   → MISSING_INTERNAL   (پول بی‌مالک! بحرانی)
elif Payment.amount_rial != amount_rial    → AMOUNT_MISMATCH    (اختلاف ریالی، بحرانی)
elif Payment.status != VERIFIED            → INTERNAL_NOT_VERIFIED  (درگاه پول گرفت، ما نگرفتیم)
else                                        → MATCHED + truth_state=STATEMENT_CONFIRMED
```

و سپس **جهت معکوس** — چیزی که کمتر دیده می‌شود:

```
Payment با status=VERIFIED در بازهٔ سند، که در فایل نیست → MISSING_GATEWAY
```

این یعنی دفتر کل ما بدهی به خیریه ثبت کرده که پشتوانه‌ای در صورت‌حساب ندارد.
**خطرناک‌ترین حالت**، چون بی‌سروصدا است.

### مرحلهٔ ۳: اقدام (`remediate_*`)

| حالت | اقدام خودکار مجاز؟ | چرا |
| --- | --- | --- |
| `MISSING_INTERNAL` | ❌ فقط صف بررسی | پول بی‌مالک؛ باید انسان مالکش را تعیین کند |
| `AMOUNT_MISMATCH` | ❌ فقط صف بررسی | اختلاف ریالی؛ هر اقدام خودکار یک قمار است |
| `INTERNAL_NOT_VERIFIED` | ✅ **خوددرمانی** | ردیف فایل می‌گوید درگاه پول گرفت و ما ثبت نکردیم ⇒ همان `reconcile_one_abandoned_payment` |
| `MISSING_GATEWAY` | ❌ فقط صف بررسی | ممکن است فایل ناقص باشد؛ آزادکردن بدهی خودکار = فاجعه |
| `DUPLICATE_IN_FILE` | ✅ علامت‌گذاری فایل معیوب | امن |

**خوددرمانی فقط یک مسیر دارد** و همان موتور داوری موجود است — نه یک مسیر موازی
تازه که دوباره‌کاری کند. این مهم‌ترین تصمیم معماری این فاز است: **یک حقیقت، یک موتور.**

## ۶. پنل حقیقت وجه — چیزی که مدیر باید در ۵ ثانیه بفهمد

به `financial_health` سه بخش تازه اضافه می‌شود:

```json
{
  "money_truth": {
    "verified_but_unconfirmed": 143,      // ما گفتیم موفق؛ صورت‌حساب هنوز تأیید نکرده
    "statement_confirmed": 8921,          // تأییدشدهٔ مستقل — تنها عددی که می‌شود به هیئت‌مدیره گفت
    "conflict": 0,                        // تناقض بین دفتر ما و صورت‌حساب — باید صفر باشد
    "last_statement_at": "2026-11-12T08:00:00Z",
    "statement_age_hours": 4.2,           // کهنگی آخرین سند
    "unresolved_findings": 3,
    "unresolved_impact_rial": 12500000
  }
}
```

**هشدارهای تازه:**
- `critical` — `conflict > 0` یا `MISSING_INTERNAL` باز (پول بی‌مالک)
- `critical` — `statement_age_hours > 48` (چشم مستقل کور شده)
- `warning` — `unresolved_impact_rial` بیش از آستانهٔ سیاست
- `warning` — `integrity_ok=False` روی هر سندی (فایل معیوب)

## ۸. آزمون‌ها — چه چیزی قفل می‌شود

**ورود و صحت فایل**
1. همان فایل دوبار ⇒ همان سند، نه دو سند (idempotency با sha256)
2. مبلغ فارسی «۱٬۲۵۰٬۰۰۰» ⇒ `1250000` (`int`، بدون خطای گردکردن)
3. مبلغ اعشاری «1250000.75» ⇒ رد صریح (ریال عدد صحیح است، نه اعشار)
4. `declared_total ≠ computed_total` ⇒ `integrity_ok=False`
5. ردیف بدون `authority` ⇒ رد ردیف با گزارش، نه کرش کل سند

**تطبیق**
6. ردیف منطبق ⇒ `MATCHED` + `truth_state=STATEMENT_CONFIRMED`
7. ردیف بدون پرداخت داخلی ⇒ `MISSING_INTERNAL` (هشدار critical)
8. اختلاف مبلغ ⇒ `AMOUNT_MISMATCH`
9. پرداخت داخلی `VERIFIED` که در فایل نیست ⇒ `MISSING_GATEWAY`
10. ردیف تکراری در فایل ⇒ `DUPLICATE_IN_FILE`
11. سند با `integrity_ok=False` ⇒ تطبیق اجرا می‌شود ولی **هیچ خوددرمانی‌ای نمی‌کند**

**خوددرمانی**
12. `INTERNAL_NOT_VERIFIED` زیر سقف ⇒ همان `RECOVERED` موتور داوری، بدون کد تکراری
13. `INTERNAL_NOT_VERIFIED` بالای سقف ⇒ صف بررسی، نه اقدام
14. `auto_heal_enabled=False` ⇒ هیچ اقدام خودکاری
15. خوددرمانی دوباره اجرا شود ⇒ idempotent (موتور داوری قبلاً حل کرده)
16. `MISSING_GATEWAY` هرگز خودکار حل نمی‌شود

**ناورداها**
17. تراز دفتر کل پس از هر خوددرمانی
18. هیچ ردیفی بی‌آنکه `match_status` بگیرد رها نمی‌شود
19. `reconcile` با `dry_run` هیچ نوشتنی نکند
20. پنل حقیقت وجه اعداد درست بدهد

**معماری**
21. `ledger` نباید از `contributions` import کند (DAG)
22. منطق تطبیق در `services` باشد نه `views` (بدون `.save()` در ویو)

## ۹. چرا این انتخاب، و نه یک فیچر جذاب‌تر

سه گزینهٔ جذاب‌تر روی میز بود: **بازپرداخت جزئی**، **کمک ماهانه (Recurring)**، **وب‌هوک**.
هیچ‌کدام انتخاب نشد، به این دلیل‌ها:

- **Recurring** بزرگ‌ترین فیچر است ولی روی پایه‌ای می‌نشیند که هنوز «خودگواه» است.
  ساختن فیچر درآمدی روی حقیقتی که تأیید مستقل ندارد، بدهی فنی را دو برابر می‌کند.
- **بازپرداخت جزئی** ارزشمند است ولی `PaymentRefund` امروز `OneToOne` است و تغییرش
  یک مایگریشن پرریسک روی مسیر پول است — بدون لایهٔ تطبیق، اگر جزئی بازپرداخت کنیم
  نمی‌توانیم بفهمیم درست انجام شد یا نه.
- **وب‌هوک** زیباست ولی زرین‌پال API وب‌هوک پایدار نمی‌دهد؛ ساختنش یعنی ساختن چیزی
  که در تولید کار نمی‌کند. صورت‌حساب، **همیشه** در دسترس است.

این فاز، **پیش‌نیاز** آن سه است: بدون آن، هر فیچر مالی بعدی روی شن ساخته می‌شود.

## ۱۰. آنچه آگاهانه خارج از دامنه است

- **دریافت خودکار فایل از API بانک/درگاه**: زرین‌پال API عمومی صورت‌حساب نمی‌دهد.
  ورود دستی/زمان‌بندی‌شده از فایل، تنها مسیر واقعی است. آداپتور آماده است تا وقتی
  API اضافه شد، فقط یک `parse_*` تازه لازم باشد.
- **بازپرداخت جزئی**: فاز ۴.
- **تطبیق زنده بدون فایل** (استعلام نقطه‌ای از درگاه): همان `verify()` است — همان
  خودگواهی که می‌خواهیم بشکنیم. عمداً نیست.
